## 1. 查證過的事實

- 待標記的條件已有：`booking/pending_kinds.condition("awaiting_attendance")`（已確認、場次已開始），後台總覽與案件列表用同一個。
- 招生訪視的下次聯絡：`admissions/follow_up.update_follow_up`（樂觀鎖、寫 `follow_up_updated` 歷程、已註冊或已退出丟 `FollowUpNotAllowed`）。
  後台快捷鍵是「明天 10:00／3 天後／1 週後」，都是台北 10:00（`admin/src/admissions/followUp.ts`）。
- 家長取消：`access_routes.parent_cancel` ＝ 鎖列重讀場次 → 檢查線上異動期限（各校設定，停課日不受限）→ `workflow_service.cancel(actor=PARENT)`，
  同交易排家長取消通知（Email／LINE）。
- 家長 postback：一對一事件的 `source.userId` 一定有；綁定是 `line_parent_links(account_key, line_user_id, visit_request_id)`。
- 地圖網址：後台「五校介紹」可填 `map_url`（`content/schemas.is_map_url` 驗過），沒填官網用地址組 Google 地圖搜尋（`web/app/utils/site-links.campusMapUrl`）。

## 2. 「待標記」（項目 1）

- 指令：整則訊息是「待標記」；@官方帳號時同樣認得。@ 選單多一顆「待標記」。
- 內容：群組服務的校區裡，`awaiting_attendance` 的案件（排除測試／重複、已匿名化），**新的在前**（最近剛結束的最可能記得）。
  卡片同名單（每筆有已到場／未到場），超過 11 筆照舊寫「另有 N 筆，請開後台」。
- 標題「待標記到場」；沒有就回「目前沒有待標記到場的參觀。」

## 3. 指定日期、下週（項目 2）

- 指令：「11/28 參觀」（月／日，全形數字與「／」先轉半形，「參觀」前可有空白）、「下週參觀」（下週一到週日）。@官方帳號時也認「11/28」「下週」。
- 年份：今年的這一天早於今天超過 183 天就算明年（12 月查 1 月）。不存在的日期（2/30）不算指令、不回應。
- 查過去的日期：不列名單，回「已經過去的日期請到後台查看；還沒標記到場的請輸入「待標記」。」（名單只列已確認的，過去的日子列出來會誤以為沒人來）。
- @ 選單多一顆「下週參觀」；新成員說明改列全部指令。

## 4. 卡片多帶人數與取消方（項目 3）

- 群組推播卡片：有參觀人數就多一列「參觀人數 N 位」；取消卡片多一列「取消方」：家長取消／園方取消／占位逾期（`cancel_reason`）。
- 名單與摘要每筆也多「參觀人數」。兩個欄位都不是個資（10-05 裁定不放的是電話、Email、孩子資料）。

## 5. 到場結果卡的「下次聯絡」（項目 4）

- 有招生訪視的結果卡多一排「下次聯絡：明天／3 天後／1 週後」（postback `rff:<訪視>:<1|3|7>`），時間是台北日期 N 天後 10:00（同後台快捷鍵）。
- 寫入：同其他結果欄位按鈕（鎖訪視列重讀、群組授權、未匿名化、未退出、招生入學開著），走 `follow_up.update_follow_up`，
  版本衝突重讀一次；已註冊或已退出回「這筆已不能排下次聯絡」。負責人不動（群組對不到後台帳號）。
- 不做二次確認（可以再按來更正）。回覆「已記錄：下次聯絡 11/26（三）10:00」。
- 稽核沿用 `line.group.recruitment_field`，`field=follow_up_at`、`value`＝天數（1／3／7）。招生歷程照常寫 `follow_up_updated`（actor 為空）。

## 6. 家長卡片的「導航」（項目 8）

- 預約成功、已變更、參觀提醒三種卡片多一顆「導航到園所」（link 樣式）：後台填了驗證過的地圖網址就用它，否則用地址組 Google 地圖搜尋；
  都沒有就不放。取消、停課卡片不放。
- 只加在 LINE 卡片；Email 照舊（信裡已有地址）。

## 7. 參觀提醒的「會準時到」（項目 9）

- 參觀提醒卡（不是停課內容時）多一顆「會準時到」（postback `ivy:pa:<案件>`，`displayText`「會準時到」，在家長的聊天室留下這句）。
- webhook 收到一對一 postback：這個 LINE 綁在這筆預約上、這個帳號是這校目前的家長通知帳號、預約還是已確認、場次還沒結束、那天沒停課
  → 記下 `attendance_confirmed_at` 與 `attendance_confirmed_slot_id`（新欄位，migration），回「收到，期待與您見面！」。
  同一個場次已回覆過就只回同一句、不再寫。條件不符回「這筆預約已無法回覆，輸入「我的預約」可以查看目前的預約」。
- 改期後舊的回覆自動失效：只有 `attendance_confirmed_slot_id` 等於目前場次才算（不必改所有改期路徑）。
- 顯示：
  - 案件歷程一筆「家長回覆會準時到」（來源「家長（LINE）」），同一場次只記第一次。
  - 後台案件明細「家長資料」多一列「家長回覆：會準時到（11/27 20:13，LINE）」（已確認時才顯示）。
  - 群組名單、摘要、待標記每筆多一列「家長回覆：會準時到」。
- 新欄位：`visit_requests.attendance_confirmed_at`、`attendance_confirmed_slot_id`（都可為 NULL，不是個資，匿名化不清）。
  API 回 `parent_attendance_confirmed_at`（場次對得上才有值）。

## 8. 「我的預約」直接取消（項目 11）

- 「我的預約」每張卡：線上異動期限還沒過（或那天停課）多一顆「取消預約」；過了就寫「已過線上修改期限，要取消請來電 <電話>」。
- 按「取消預約」（`ivy:pc:<案件>`）：不寫入，檢查同下面第 3 點，回確認卡「確定取消這次參觀？」＋校區、日期與場次，
  按鈕「確定取消」（`ivy:pcok:<案件>:<token>`，`displayText`「確定取消」）、「不取消」（`ivy:pcno`，回「好的，預約保留不變。」）。
- token 沿用群組按鈕的無狀態 HMAC（綁動作與案件 id，5 分鐘），過期回「這個確認已過期，請到「我的預約」再按一次」。
- 確認時：鎖案件列重讀場次 → 綁定仍在（同帳號、同 userId）且帳號仍是這校的家長通知帳號 → 已確認 → 期限沒過（停課日不受限，同 `require_change_window`）
  → `workflow_service.cancel(actor=LINE 家長)`；同交易照舊排家長取消通知（Email 與 LINE 各一則，LINE 那則**會用掉 1 則額度**，和官網取消一樣）。
  回「已取消這次參觀預約。想再參觀歡迎重新預約。」再按一次「確定取消」回「這筆預約已無法取消…」，不重複寫入。
- 歷程來源新增 `line_parent`（後台「家長（LINE）」，時間線用家長的顏色）；稽核 `line.parent.cancel`（metadata 只有帳號代碼）。
- 限流沿用家長一對一的每分鐘 10 次（代碼、我的預約、按鈕共用）。
- 授權等同修改連結：綁定是拿修改連結取代碼才建得起來，園方撤銷或重發連結、更正 Email 都會一併解除（11-16 §10）。

## 9. 不做

- 群組裡輸入任何文字欄位；家長端改期（要選場次，留給修改頁）；Email 版的導航與「會準時到」。
- LINE 取消時省掉推播的那 1 則（要繞過 outbox 的管道判斷，不值得）。

## 10. 施工結果（2026-11-25）

- 新模組 `backend/app/notifications/line_parent_actions.py`（家長按鈕）；群組沿用 `line_group_commands`、`line_group_actions`、`line_digest`。
- migration `f2b7c4e9a813` 只新增 `visit_requests.attendance_confirmed_at`、`attendance_confirmed_slot_id` 兩個欄位。
- 歷程來源 `line_parent` 在 `analytics_service.cancel_reason` 算家長取消（否則從 LINE 取消會被記成園方取消、取消信寫「園方已取消」）。
- 「我的預約」過了期限仍保留「查看或修改」連結（頁面看得到內容，只是不能改），只拿掉「取消預約」。

  token（過期、偽造）、去重（重按會準時到、重按取消）、改期後回覆失效、卡片內容不含個資。

- 沒辦法自動驗：真的 LINE 上按鈕的呈現、`displayText` 在一對一聊天的樣子、導航在手機 LINE 開啟的行為。
