## 1. 目的、範圍與原則

- 目的：總部不用每週自己打指令看數字；園方早上知道前一天有多少人按了電話或 LINE；四校的廣告名單和義華一樣進群組。
- 不做：校區群組的週報／月報（使用者指定總部）；PNG 圖檔；為了點擊數另外推一則；在群組填欄位、改期、查姓名電話（前幾輪裁定）。
- 不可發生：同一份報表重複推；報表數字和後台成效統計對不起來；卡片或 altText 出現電話、Email、孩子資料。
- 沿用：推播只用主帳號、不走 outbox（同每日摘要）；推成功才記已推；回覆一律 reply。

## 2. 週報（項目 7）

- **時間**：每週一 09:00–12:00 之間的第一輪定期工作（同 `stats_health` 的時段；08:00 的每日摘要先出）。這段時間沒推成功，當週就不補。
- **對象**：開了 `weekly_report` 的總部群組（`is_hq`）。
- **內容**（一則文字訊息，沿用 `stats_text` 的格式與 4800 字上限）：
  1. 「上週統計」原樣（`booking_outcomes`，依預約送出日）：各校與合計的預約、到場、未到場、取消、待標記、尚未參觀、預繳。
  2. 每校與合計在預約數後面加與前一週的差：`預約 12（前一週 9，+3）`；相同寫「持平」。只比預約與預繳兩項——其他欄位在前一週會因為後來才到場而一直變，放在一起比會誤導。
  3. **多一段「上週實際參觀（依參觀日）」**：各校到場／未到場／到場率。理由：依送出日算，上週才預約的多半還沒來參觀，那個到場率樣本很小；總部週一想知道的是上週實際來了多少人。這段是我加的，不要可以拿掉。
- 指令「週報」（總部群組才回）隨時重看同一份，reply 不計則數。

## 3. 月報（項目 8）

- **時間**：每月 1 日 09:00–12:00；對象是開了 `monthly_report` 的總部群組。1 日剛好是週一時兩份都推。
- **內容**：一張 Flex 卡片。
  - 標題「11 月月報」；合計一列：預約、到場率、預繳，各附與前一個月的差。
  - 「圖」：每校一列橫條，長度＝該校預約數 ÷ 五校最大值，條尾寫數字；下面一行小字「到場率 80%｜預繳 3」。橫條用 Flex 的 box 寬度畫，顏色走 `line_flex.BRAND`。
  - altText：「11 月月報：五校預約 N 筆」（不放個資）。
- 口徑同「上月統計」（依預約送出日）；到場率同後台（到場 ÷ 已標記）。
- 指令「月報」（總部群組才回）重看。

### 做法取捨（圖怎麼畫）

| 做法 | 取捨 | 結論 |
|---|---|---|
| A. Flex 卡片用 box 畫橫條 | 不用產圖、不用存檔、不加套件；只能畫橫條，不能畫折線 | **採用** |
| B. 後端產 PNG、放 R2、用圖片訊息推 | 可以畫任何圖；要加繪圖套件、中文字型、公開圖檔網址與清理 | 不採用：一個月一張圖不值得 |
| C. 只推文字＋後台連結 | 最省；沒有圖 | 不採用：使用者要圖 |

## 4. 電話／LINE 點擊小結（項目 12）

查到的事實：每日摘要 08:00 推，而且**只有那個群組當天有參觀才推**；08:00 當下「今天」還沒有點擊，所以摘要裡能放的是前一天的數字。

- **每日摘要多一列**：`昨天官網：按電話 3 次｜按 LINE 5 次`，放在第一張卡片。校區群組只看自己的校；總部群組列各校與「不分校區」（事件沒帶校區的）。兩個都是 0 就不放這列。
- **當天沒有參觀的群組不另外推**（會增加則數；我的決定）。改用指令補：
- **指令「聯絡」**（短字「聯絡」只在 @ 官方帳號時認；全字「今天聯絡」「昨天聯絡」）：回今天到目前為止與昨天的電話、LINE 點擊數，reply 不計則數。校區群組看自己的校，總部看五校。
- 資料來源：成效事件 `cta_click_phone`／`cta_click_line`（同後台「電話與 LINE 的時段」）；排除條件與後台成效統計一致（自動化、爬蟲、後台人員）。
- 文字要寫「按了電話鈕」而不是「來電」：按了不等於真的打通。

## 5. 四校 Meta 廣告名單通知（項目 13）

查到的事實：
- 名單同步逐校跑，新名單推到該校綁定的群組；粉專清單是「校區=粉專ID」。
- 權杖原本只有一把 `WEBSITE_FACEBOOK_ACCESS_TOKEN`，程式用它向 Graph 換每個粉專的 Page token。現在放的是義華的 Page token，換不到別校的。
- **使用者 11-26 回覆：五校粉專不是同一個 FB 帳號在管**，所以一把權杖不夠。

做法（已施工）：
- **每校可以放自己的 token**：`WEBSITE_FACEBOOK_<校>_ACCESS_TOKEN`（`YIHUA`／`MINGHUA`／`CHONGDE`／`INTERNATIONAL`／`RENWU`）。沒放的校區沿用共用的 `WEBSITE_FACEBOOK_ACCESS_TOKEN`，所以義華現況不用動。
- **名單有自己的粉專清單**：`WEBSITE_META_LEADS_PAGES`（格式同 `WEBSITE_FACEBOOK_PAGES`）。有設就以它為準，沒設沿用舊的。這樣加四校拉名單時，**不會**連帶把四校的粉專貼文同步進消息草稿（那個副作用使用者沒說要，我選擇避開）。
- 限制：各校的 token 要出自**同一個 App**（「常春藤義華校」）。`WEBSITE_FACEBOOK_APP_SECRET` 只有一份，token 來自別的 App 時 `appsecret_proof` 會對不上。所以每位粉專管理員要先被加進這個 App 的角色，再用它產生自己粉專的 Page token。

要本人做的（我不代做，步驟寫在 `deploy/README.md`「Meta 名單型廣告」段）：
1. 把四校粉專的管理員加進 App「常春藤義華校」的角色；各自產生長效 Page token（權限含 `pages_show_list`、`pages_read_engagement`、`leads_retrieval`、`pages_manage_ads`）。
2. Railway api 一次套用：四個 `WEBSITE_FACEBOOK_<校>_ACCESS_TOKEN` ＋ `WEBSITE_META_LEADS_PAGES`（五校都要列，含義華）。
3. 四校各自要有綁好的 LINE 群組，才收得到通知。

**沒驗證的風險**：App 目前是開發模式。我的印象是開發模式的 App 讀不到「沒有 App 角色的一般人」送出的名單，但沒查證；義華目前同步結果是 0 筆（廣告還沒發布），也還沒被實際驗過。擴到四校之前，先用義華一筆真的名單確認讀得到；讀不到的話 App 要送審上線（`leads_retrieval` 需要進階存取）。
