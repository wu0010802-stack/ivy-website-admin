# 後台資料匯入：在籍清冊＋歷年註冊（設計）

- 日期：2026-10-21
- 狀態：業主 10-21 核可（歷年註冊選做法 C，其餘照本文）
- 基準：一律以 `origin/main`（寫稿時 `cd7f7d6c`）為準；`feature/website-admin` 落後很多，不要讀它
- 範圍外：門牌 CSV（業主 10-21「先不管門牌」）

## 1. 為什麼要做

區域分析的「在籍學生」和招生潛力的「市佔率」各靠一份園方檔案：

| 資料 | 原檔 | 現在怎麼進正式站 | 讀者 |
|---|---|---|---|
| 在籍學生點位 | 教保資訊網「園所幼生清冊」匯出檔（.xls，內容其實是 UTF-8 HTML） | 本機 `enrolled-match`（要有門牌的本機 DB）→ 去識別 JSON → 正式站 `enrolled-import` | `GET /admin/admissions/area/enrolled`、`potential.py` 來源二與 `_capacity` |
| 歷年註冊人數 | 園方「目標執行統計表」（真的舊版 Excel，一學期一張表，99 上起） | 本機 `enrollment-history-extract`（要裝 xlrd）→ 數字 JSON → 正式站 `enrollment-history-import` | `share.py` 的 `_registered_by_year` |

兩條都要在 Mac 上跑指令、再設法在正式站跑匯入，五校裡目前只有義華匯過清冊（10-15）。目標是讓總管理者自己在後台上傳，不用指令。

## 2. 目標、非目標、反目標

**目標**
- 總管理者在後台選學校、選檔，先看預覽，確認後整校換成新資料。
- 在籍清冊：姓名、生日不離開使用者的瀏覽器；地址會送到伺服器比對，比對完就丟，不存、不寫日誌。
- 歷年註冊：姓名不離開瀏覽器（§6 做法 C）。
- 頁面上看得到每校目前匯入的是哪一份、什麼時候匯的。

**非目標**
- 門牌上傳、門牌自動同步。
- 園務管理者或其他角色上傳（業主 10-21：只有總管理者）。
- 歷年註冊的「清除」功能（CLI 本來就沒有；要清掉可以匯入正確的檔覆蓋）。
- 改動既有 CLI 的行為；CLI 保留當備用。
- 新的資料表或 migration（現有 `enrolled_rosters`、`enrolled_student_points`、`campus_term_enrollment`、操作紀錄都夠用）。

**反目標**（技術上能動，但發生就算失敗）
- 地址出現在任何資料表、日誌、操作紀錄、錯誤回應、前端持久儲存（localStorage／sessionStorage／IndexedDB／Pinia 持久化）裡。
- 姓名或生日出現在任何送到伺服器的請求裡。
- 為了上傳把 API 或 web 代理的 1 MB 本文上限整體放寬。
- 正式映像因此必須裝 xlrd。
- repo（程式、測試、fixture、規格、commit 訊息）出現任何從真實清冊或真實統計表推出的資料。

## 5. 在籍清冊

### 5.1 瀏覽器端

1. 使用者選檔（`.xls`），以 UTF-8 讀成文字，`DOMParser('text/html')` 解析（DOMParser 產生的文件不執行腳本、不載入資源）。
2. 規則照 `backend/app/admissions/enrolled/roster.py`：
   - 找第一列同時有「出生日期」「通訊地址」的 `<table>`，依表頭文字認欄；`td`、`th` 一視同仁，格子文字 trim。
   - 每列欄數要和表頭相同；出生日期要是 `YYYY/MM/DD`；錯誤訊息只寫第幾列，不寫地址。
   - 列印日期在任何格子裡以「列印日期：YYYY/M/D」找；找不到就讓使用者選日期（同 CLI `--roster-date`）。
   - 其他欄（編號、姓名、性別、入學日期、實際年齡）不放進任何變數以外的地方，讀到就丟。
3. 班別：學年 ＝ `currentTerm(清冊日期)` 的學年（`admin/src/admissions/academic.ts` 已有），班別 ＝ `roster.py` 的 `roster_grade` 規則（`gradeForBirthday` 之外再加兩條：9/1 未滿 2 歲 → 幼幼班、滿 6 歲以上 → 其他）。admin 目前沒有 `roster_grade` 的 TS 版，要補，並和 Python 共用案例（現有 `contracts/ivy-recruitment/grade-cases.json` 的做法）。
4. 送出 `{campus_key, roster_date, students: [{grade, address}]}`。學生順序在送出前打亂或排序，不保留清冊列序（現在的 JSON 也刻意不保留列序）。
5. 地址只存在這次請求用到的區域變數；預覽回來後不保留。要重新預覽就重讀檔案。

### 5.2 伺服器端

**預覽**（不寫資料庫）
- 把 `match_roster` 的核心拆成吃 `(班別, 地址)` 的版本，CLI 的 `match_roster` 改成先用 `roster_grade` 算班別再呼叫它，行為不變。學年由伺服器自己從 `roster_date` 算。
- 前提錯誤沿用 `MatchError` 訊息（門牌沒匯入、本校沒有已發布校址座標）。
- 回傳：
  - 報告（結構化，不是 CLI 的文字行）：共幾位、有點幾位與比例、各比對等級人數、補區方式人數（含推定幾位）、各班人數、沒有點的學生清單（等級／原因／`masked_address` 的街路名，沒有就空白）。
  - 去識別資料：和現在 `ivy-enrolled-points/1` 相同的內容（`campus_key`、`roster_date`、`school_year`、`doorplate_version`、`students[grade, district, village, match_level, unlocated_reason, lat, lng]`），依現在的規則排序。
  - 這份資料夠不夠匯入（比例 ≥ 90%）。
- 上限：一次最多 2000 位、地址最長 120 字，所以本文一定在 1 MB 內，**不改** `body_limit.py` 和 `web/shared/request-guard.ts` 的白名單。
- 這個端點的 422 不可回傳輸入值（FastAPI 預設的 422 會帶 `input`，也就是地址）；改用 `describe_error` 那種只給位置與種類的寫法。
- 不寫操作紀錄（沒有改資料）。

**確認匯入**
- 本文就是預覽回來的去識別資料，用現有 `EnrolledRosterIn`（extra=forbid、里名白名單、座標範圍）驗證後走 `replace_roster`。地址只在預覽送一次，這一步沒有地址。
- 額外檢查：
  - 有點比例 ≥ 90%，否則拒絕（業主確認的「擋下」；CLI 的 `--allow-low-hit` 保留當備用）。
  - `doorplate_version` 等於正式站使用中的門牌版本，否則 409「門牌已換版，請重新預覽」。
  - `school_year` 等於 `current_term(roster_date)` 的學年。
- 整校取代、寫操作紀錄、commit。
- 已知取捨：總管理者可以自己捏一份點位送進來。這和現在 CLI 匯入 JSON 的信任程度一樣，不另外簽章。

**清除**：沿用 `clear_roster`，寫操作紀錄。

### 5.3 不寫進日誌

- `match_roster` 已經把逐筆比對的例外包成不含地址的 `MatchError`（`from None`），新核心要保留這個做法。
- 確認預覽路徑上任何 `logger` 呼叫、例外訊息、操作紀錄 metadata 都不含地址；測試要用 caplog 斷言。
- 確認 Nuxt 代理與 admin 的 API client 不記錄或回報請求本文（寫稿時沒看到，實作時再確認一次）。

## 6. 歷年註冊

原檔是真的舊版 Excel（BIFF），瀏覽器要讀就得加試算表套件。可用的只有 SheetJS：npm 上的 `xlsx@0.18.5` 有已知漏洞（CVE-2023-30533、CVE-2024-22363），新版只從 `cdn.sheetjs.com` 發布（寫稿時已知 0.20.3，實作時查最新）。

真檔格式（10-21 主 session 用 xlrd 只讀中繼資料，沒印任何格子內容）：義華 `目標執行統計表1150915xls.xls` 是 **BIFF8**（`biff_version` 80）、`codepage` 1200（UTF-16，字串本來就是 Unicode），33 張表、250 KB。10-20 規格 §3.1 寫的「Big5 代碼頁」不正確，所以 SheetJS 不需要 codepage 表（cpexcel），xlwt 產的 BIFF8 合成檔也有代表性。

SheetJS 實測（10-21，`cdn.sheetjs.com` 最新仍是 0.20.3，Apache-2.0）：
- `dist/xlsx.mini.min.js` 讀 XLS 直接丟 `parse_xlscfb is not defined`（mini 沒有 BIFF）；`dist/xlsx.core.min.js` 在 Node 讀 xlwt 合成檔也失敗。
- 套件入口 `xlsx.mjs`（`import * as XLSX from 'xlsx'`）讀得了 xlwt 合成檔，也寫得出 BIFF8（`bookType: 'biff8'`，測試可以自己產檔）。
- 用 `xlsx.mjs` 讀義華真檔（只印計數）：33 張表名全是「學年＋上／下」、33 張都找得到四個年級列、第 2／3 列格子只有字串與空白。

### 做法 C：瀏覽器只擷取表頭與年級列，伺服器用現有規則解析（採用）

- 瀏覽器用 SheetJS 讀活頁簿，每張工作表只取：
  - 表名；
  - 第 2、3 列（0 起算，與 `workbook.py` 的 `BLOCK_ROW`／`SUBHEADER_ROW` 相同）整列；
  - 從第 4 列往下，第 0 欄（去掉所有空白後）是「大班」「中班」「小班」「幼幼班」「總人數」的列，各取第一個，找齊就停。這幾列的其他格只保留數字格與「去空白後全是數字」的文字格；其他文字格換成一個固定的「非數字」記號，不送內容。
  - 其他列（標題、備註、姓名）一律不擷取。
- 送出 `{campus_key, sheets: [{name, width, rows: {列號: [格子…]}}]}`，格子只有「空、數字、文字、非數字記號」四種。
- 伺服器把 `workbook.py` 拆成兩層：
  - 純解析層（新模組，正式站可以 import，不依賴 xlrd）：吃上面那種格子表，跑現在全部的規則（依表頭文字認欄、99／100 學年舊版型、日期欄、總人數核對與警告、錯誤訊息只寫表名與欄名）。
  - xlrd 轉接層（留在 `workbook.py`，只在 extract 群組）：把 xlrd 工作表轉成同一種格子表，CLI 照舊。
  - 「非數字記號」在需要人數的欄位上要報和現在一樣的「不是整數」錯誤，所以解析結果和 xlrd 路徑完全相同。
- 守門測試 `test_production_modules_never_import_xlrd` 要繼續過（新的解析層加進它檢查的模組清單）。
- SheetJS 只在「資料匯入」分頁動態載入，不進後台其他頁面的 bundle。
- 本文：約 40 張表 × 7 列 × 30 欄，遠小於 1 MB。

### 做法 B：整個檔案交給伺服器，用現有程式解析（不採用，比較紀錄）

- 瀏覽器直接上傳原檔；伺服器寫進暫存檔（`mkstemp`，`finally` 刪除，同素材上傳）後跑現有 `parse_workbook`。
- 程式最少，但：
  - 原檔（含備註裡的姓名）會經過伺服器記憶體和暫存檔；不讀、不存、不寫日誌，但確實經過。
  - xlrd 要從 extract 群組搬進正式依賴，守門測試要改掉。
  - 真檔 250 KB，一年多兩張表，幾年內都在 1 MB 本文上限內，現在不用放寬；哪天超過才要在 `body_limit.py` 和 `web/shared/request-guard.ts` 各加白名單。
  - 解析失敗時要給遮罩表頭（同 CLI `--headers-only`），得另做一支回傳遮罩表頭的端點。

### 不採用：做法 A（把整套解析規則改寫成 TypeScript）

約 330 行規則會有 Python、TS 兩份，日後園方改版型要改兩邊、兩邊的案例要長期對齊。做法 C 用約幾十行的「擷取」換掉這個成本。

### 兩種做法共同的部分

- 預覽：伺服器解析後回傳 `ivy-enrollment-history/1` 的內容（數字＋警告）和摘要（學期範圍、列數），不寫資料庫。
- 確認匯入：本文就是那份數字資料，用現有 `EnrollmentHistoryIn` 驗證後走 `replace_history`（整校取代），寫操作紀錄。
- 解析錯誤直接顯示 `WorkbookError` 的訊息（本來就只含表名與欄名）。

## 7. 頁面

- 位置：`/admin/admissions-stats` 加一個子分頁「資料匯入」（網址 `sub=imports`），和「招生潛力」一樣不看入學學年學期；學校用頁首現有的校區下拉。只能對單一學校操作。
- 招生開關關閉時同整頁「尚未啟用」。
- 兩個區塊，在籍清冊在上、歷年註冊在下，每塊：
  1. **目前資料**：
     - 在籍：清冊日期、學年、人數（有點幾位）、比對用門牌版本、匯入時間；比對用的門牌版本和使用中的不同時，加一行「門牌已換版，可以重新上傳清冊」。
     - 歷年：學期範圍、列數、匯入時間。
     - 沒有資料時寫「還沒有匯入」。
  2. **選檔**：一行說明送出什麼（在籍：「只會送出地址和班別，地址比對完不保存」；歷年：做法 C 是「只會送出表頭和各年級的數字」）。
  3. **預覽**：
     - 在籍：數字摘要、各班人數、比對等級與補區方式、沒有點的學生（等級／原因／街路…）。比例不到 90% 時寫明原因，「確認匯入」停用。
     - 歷年：學期 × 年級的註冊人數表、警告清單。
  4. **確認匯入**：按下後說明會整校換掉，成功後重新載入「目前資料」。
  5. 在籍另有「清除這校在籍資料」，放在次要位置，要再確認一次。
- **選錯校的防呆**（校區來自頁首下拉、會跨頁帶著，選錯就整校蓋掉別校；90% 門檻擋不住，因為他校學生也住高雄）：
  - 預覽和確認對話框都用大字寫「匯入到：〇〇校」。
  - 在籍：清冊第一個表格（非學生列）有園所名稱（10-21 確認含「常春藤」字樣、不含校區簡稱，所以不做自動比對），瀏覽器在預覽旁顯示「檔案上的園所：…」給使用者自己核對；這段文字不送出。
  - 兩種資料都和這校目前的資料並列：在籍是舊清冊日期與人數 → 新的；歷年是兩邊都有的學期，註冊人數不同的列出來。
  - 統計表標題列只有「常春藤」、沒有校區名，無法核對檔案屬於哪一校。
- **會被刪掉的學期**（歷年）：整校取代時，資料庫裡有、新檔裡沒有的學期列在預覽裡，有的話要多勾一個「我知道這些學期會被刪掉」才能確認（園方若只給部分學期，才不會靜靜斷掉市佔率走勢）。
- **解析失敗時**（歷年）：做法 C 在頁面上顯示各表的第 2、3 列與第 0 欄年級標籤（同 CLI `--headers-only` 的遮罩規則，其他第 0 欄格子顯示「…」），只在瀏覽器顯示、可複製，讓業主不用跑 CLI 也能把表頭交給開發者看。
- 比對可能要幾秒到十幾秒，按鈕要有處理中狀態，期間不能重複送出。
- 文字遵守後台既有字級 token 與說明收合的慣例。

## 8. 權限、開關、操作紀錄

- 所有新端點：`admissions.stats`＋`_require_campus(..., campus_key)`，同招生統計其他端點；招生開關關閉時的行為也照它們。
- 前端分頁只有總管理者看得到（整頁本來就是）。
- 操作紀錄：在籍匯入、在籍清除、歷年匯入各一種 action，`target_type` 用校區，metadata 只放數字與版本（人數、有點人數、清冊日期、門牌版本；列數、學期範圍）。命名照現有招生 action 的慣例。
