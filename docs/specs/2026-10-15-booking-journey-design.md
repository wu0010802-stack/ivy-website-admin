## 1. 背景與目標

後台有兩套資料：預約端（`visit_requests`，家長或園方約的參觀）與招生端（`recruitment_visits`，到場後的訪視、預繳、註冊、退出）。現有統計各看一半：

- 預約端「參觀預約」頁有取消率、取消原因、到場率、沒來率，但止於「已完成參觀」。
- 招生端漏斗與統計分析從「已訪視」才開始（含手動新增的），預繳速度只有一個天數指標（參觀日到預繳）。
- 兩套資料唯一的連結 `recruitment_visits.visit_request_id` **沒有任何統計用到**；能同時看到兩邊的只有單筆「預約明細家庭頁」。

所以招生人員問不出：「官網預約進來的家庭，在哪一步、什麼時候流失？」本案補這條路徑：預約 → 到場 → 有招生訪視 → 預繳 → 註冊，加上各段之間花多久，以及家庭離開的時點。

### 1.1 成功標準

1. 招生入學 → 統計分析多一個子分頁「預約全程」，選定校區與期間後，看到同一批預約案件從頭到尾的人數與各階段比率（附分子分母）。
2. 看得到家庭離開的位置與時點：取消（距參觀日幾天、家長或園方）、沒來、時間已過未標記、已到場但沒有訪視、參觀後未預繳（觀察中／逾期／冷名單）、預繳後退出（退預繳、退註冊）。
3. 看得到各段花多久：預約提前量、參觀到預繳、預繳到註冊、預繳到退出（中位數與筆數）。
4. 涵蓋範圍誠實寫明：這個漏斗只含有預約案件的家庭；沒有預約案件的訪視（現場參觀、舊名單補登）與沒有連到訪視的已到場案件，各自列筆數。
5. 只描述過去，不預測；不新增 migration；唯讀，不寫稽核。

### 1.3 不做

- **預測與評分**：不推估觀察中的家庭最後會不會預繳，不替個別家庭打分（既有規則 R:34）。
- **退出原因統計**：`withdraw_reason` 是自由文字、沒有代碼，原因代碼列為另案（預繳速度規格 §3.2）；本案只看退出的時點。
- **首次聯絡延遲與聯絡紀錄分析**（R:126 已裁定不列指標）。
- **預約提前量與「額滿」的關係**（場次使用情況規格 §1.3 不做「提前幾天就額滿」）。
- **跨校合併**：單一校區，與其他統計頁一致；五校比較另案。
- 補欄位或回補舊資料；公開官網顯示；匯出含個資（CSV 只有聚合數字）。

## 3. 設計

### 3.1 母體與口徑

見 §1.2 J3–J12。補充：

1. **批次與期間**：批次是「預定參觀日在 `from`～`to` 之間、已過參觀時間」的預約案件。預定參觀日算不出來的案件（舊資料，無場次且無 `completed` 事件）不進批次，列在涵蓋說明。
2. **各階段人數與比率的關係**（皆為同一批案件）：

   | 階段 | 人數（曾經到達） | 比率（分子／分母） |
   |---|---|---|
   | 預約案件 | N | — |
   | 已到場 | 已到場 | 到場率＝已到場／（已到場＋沒來）；取消率＝已取消／預約案件 |
   | 有招生訪視 | 已到場且連到訪視 | 有訪視／已到場 |
   | 預繳過 | 見 J7 | 預繳過／有訪視 |
   | 註冊過 | 見 J7 | 註冊過／預繳過 |
3. **離開的類別**：沒走到「預繳過」的家庭恰好分成這幾類（互斥）：取消（家長、園方、其他）、沒來、時間已過未標記、已到場但沒有訪視、參觀後未預繳（觀察中、逾期、冷名單）。預繳後退出（退預繳、退註冊）是「預繳過」裡的子集，另列，不從上面幾類扣。
4. **取消時點分區**以取消日與預定參觀日相比；取消日在預定參觀日之後的另列「參觀日之後才取消」。

### 3.2 計算與 API

1. **端點**：`GET /admin/admissions/journey`（`admissions/routes.py`），參數與權限見 J13；程式放新檔 `backend/app/admissions/journey.py`，路由、schema 接在既有招生模組，契約重新產生。
2. **載入**：以校區、預定參觀日範圍取出批次案件；補它們的事件（`rescheduled` 次數；`completed` 的台北日，只給提早到場釋出場次者算預定參觀日用）、連到的招生訪視、這些訪視的 `deposit_added` 最後一筆時間。以集合式查詢取回，在 Python 裡分類與彙總；單次請求最多 400 天的批次。預定參觀日算不出來的案件無法歸到期間，改以預約送出日（台北日）落在期間內的計入涵蓋說明的 `undated_cases`（計畫裁定 P2）。
3. **回傳**（欄位名是設計，實作時以 pydantic schema 為準）：
   - `filters`：`campus_key`、`from`、`to`、`source`；`as_of` 放在回應最上層，不在 `filters` 內。
   - `cases`：預約案件數、依來源（`web`、`phone`、`line`、`walk_in`、`external`）的數目。
   - `visit_outcomes`：已到場、沒來、已取消（含 `parent`、`staff`、`other`）、時間已過未標記。
   - `admissions`：有訪視、已到場但沒有訪視、預繳過、註冊過、預繳後退出（`from_deposit`、`from_enrolled`）、參觀後未預繳（`observing`、`overdue`、`cold`）。
   - `rates`：每個比率的 `key`、`numerator`、`denominator`、`pct`（分母 0 為 null）。
   - `timing`：`lead_days`（預約提前量）、`cancel_before_visit`（各分區與家長／園方）、`visit_to_deposit`、`deposit_to_enrolled`、`deposit_to_withdrawn`；`lead_days`、`visit_to_deposit`、`deposit_to_enrolled`、`deposit_to_withdrawn` 各有 `median`、`n`、`excluded`（沒有時間或負值而不納入的筆數）；`cancel_before_visit` 沒有 `median`，有 `n`、`excluded` 與家長、園方、其他三組分區計數。
   - `rescheduled`：改期過的案件數（分子）與預約案件數（分母）。
   - `coverage`：`visits_without_request`、`completed_without_visit`、`undated_cases`。
4. **不變式**（測試釘住）：(a) 預約案件 ＝ 已到場 ＋ 沒來 ＋ 已取消 ＋ 未標記；(b) 已到場 ＝ 有訪視 ＋ 已到場但沒有訪視；(c) 有訪視 ＝ 預繳過 ＋ 觀察中 ＋ 逾期 ＋ 冷名單（預繳過已含所有退出者，所以不會有「退出但從未預繳」的第三種）；(d) 預約案件 ＝ 預繳過 ＋ 已取消 ＋ 沒來 ＋ 未標記 ＋ 已到場但沒有訪視 ＋ 觀察中 ＋ 逾期 ＋ 冷名單；(e) 註冊過 ≤ 預繳過 ≤ 有訪視 ≤ 已到場，預繳後退出 ≤ 預繳過。
5. **時區**：所有「日」都是 Asia/Taipei；以 UTC 存的時間先換成台北日再比較。
6. **不寫稽核、不寫任何資料。**

## 6. 風險與限制

1. **連結涵蓋率**是最大限制：招生開關關閉期間到場、事後沒補建的案件顯示為「已到場但沒有訪視」，漏斗後半段會偏低；數字照寫、不估算，涵蓋說明列筆數。
2. **預繳日會失真**：補登或事後標記讓天數偏長（與預繳速度同一限制）；沒有 `deposit_added` 事件者不納入天數。
3. **「時間已過未標記」另列**：不算到場也不算沒來，近期批次這類會比較多。
4. **近期批次的後半段還在變**：參觀後未預繳的家庭歸在「觀察中」，不預測。
5. **預繳後退出人數少**：天數只給中位數與筆數，不足 20 標「樣本較少」。
6. **退出原因不統計**（自由文字、無代碼，另案）。
7. **權限**：新頁需要 `admissions.read`。10-13 留下的「editor／readonly 失去預約數字入口」問題，這一頁不能補回，仍待業主裁定。
8. **與其他 session 的協調**：`StatsTab.vue`、`useAdmissionsFilters.ts`、契約檔可能同時被改；開工前與推送前都要對 `origin/main`，有衝突就 merge 並重跑契約。
9. **未驗證**：沒有登入正式後台看過畫面，也沒查過正式資料的連結率。

### 8.1 與規格的差異（計畫裁定）

- **P1**：摘要句直接寫在 `JourneyTab.vue`，不另開 `JourneySummary`；區塊元件是 `JourneyFunnel`、`JourneyExits`、`JourneyTiming` 三個（§3.3）。
- **P2**：預定參觀日算不出來的案件，以預約送出日（台北日）落在期間內才計入 `coverage.undated_cases`，且不進批次（§3.2）。
- **P3**：`to` 截到今天之後若 `from > to`（例如整段在未來）回 422 `INVALID_DATE_RANGE`；回應 `filters.date_to` 是截過的日期。
- **P4**：「每案一類」的 SQL CASE 直接 import `booking_outcomes_service._outcome`（私有函式），不複製，與「預約結果」不會漂移；該檔的 `upcoming` 在查庫時丟掉。
- **P5**：預定參觀日的 SQL 照抄 `booking/routes.py` 的 `_visited_on_column`，不 import（它在路由模組裡、綁了列表查詢）；日後改列表的參觀日算法，這裡要同步，提早到場的案例有測試釘住。
- **P6**：預繳過＝`has_deposit`、`enrolled` 或 `withdrawn_at` 非空（J7 已改）。
- **P7**：網址參數 `jp`（`90`、`180`、`365`、`custom`，預設 `90` 不寫）、`jf`／`jt`（自訂起訖，只在 `jp=custom` 寫）、`js`（`web`、`assisted`，`all` 不寫），只在 `tab=stats&sub=journey` 時寫進網址、離開就拿掉。
- **P8**：e2e 用 `renwu`，種子以家長與幼生姓名「E2E旅程」開頭標記，每個案例前後都清除（含失敗）。原先「沒有其他 spec 動 `renwu`」的前提不成立，見 R7。
- **P9**：預約提前量用批次內所有案件（含取消、沒來）；中位數到小數一位；畫面上整數值不寫小數點（5 天），非整數寫一位小數（6.5 天）。
- **P10**：`deposit_to_withdrawn` 只給合計（退預繳與退註冊合在一起）一組天數。

### 8.2 實作中的裁定

R 編號是實作期間的裁定序號，與前文「R:行號」（指向 09-30 分析報告）無關；§8.1、§8.2 的 P／R 條目都是實作中的裁定，不是使用者逐項核可。

- **R3（J15 更正）**：涵蓋說明三個筆數裡，只有 `visits_without_request` 不受來源篩選；`completed_without_visit` 與 `undated_cases` 是被篩選批次內的案件，跟著來源篩選，且 `completed_without_visit` 必須等於 `admissions.completed_without_visit`（不變式 (b)）。原稿「三個都不受篩選影響」不成立，J15 已改。
- **R4（J10 的落實）**：取消時點「缺取消時間」的筆數會顯示：取消時點表在時接在表的說明後面；表被隱藏（取消都缺時間）時，另在離開表下方寫一行。措辭「另有 N 筆沒有取消時間，不納入」。取消時點只會因缺取消時間而排除，取消日晚於預定參觀日者歸「參觀日之後才取消」。
- **R5**：離開表三個取消列的時點欄：有取消時間資料時寫「距參觀日見下表」，取消都缺時間時寫「沒有取消時間可比對」，完全沒有取消時寫「—」。
- **R6**：預約全程的 CSV 檔名是「招生統計-預約全程-<表名>-<校區>-<起日>至<迄日>[-<來源>]」；日期取回應實際涵蓋的日期（迄日可能被截到今天），來源不是「全部」才加；不帶入學學年學期（這頁不分學期）。
- **R7（P8 的結果）**：`admissions-area.spec.ts` 會在 `renwu` 留下一筆沒有預約案件的訪視，所以 e2e 的涵蓋說明斷言改成「種子前同校已存在的未連預約訪視筆數 ＋ 1」，`seedJourney()` 回傳該基準。

### 8.3 其他與規格不同之處

- `as_of` 放在回應最上層，不在 `filters` 內（§3.2 已改）。
- 各段天數（含預繳到退出）筆數 1–19 標「樣本較少」，0 筆不標、中位數寫「—」（§6.5）。
- 摘要句的期間寫成「2026/07/01–2026/09/30」，不是 §3.3 範例的「2026 年 7 月到 9 月」。
- 畫面的涵蓋說明固定列「沒有預約案件的訪視」「已到場但沒有訪視」「改期過 N／M」，「預定參觀日算不出來」只在大於 0 時列。
- 取消時點表有家長、園方、其他三欄（§3.3 原寫家長與園方）。
- 漏斗每列的比率欄是該階段自己的比率（預約案件列是取消率，已到場列是到場率〔分母為到場加沒來〕，其後是有訪視比例、預繳率、註冊率、退出比例），不是一律「佔上一階段」（§3.3）。
- 摘要句不是表；畫面的表有四張：全程漏斗、家庭在哪裡離開、取消時點（有取消才顯示）、各段要花多久，各自是獨立的 `StatsDimensionTable`（J14）。
